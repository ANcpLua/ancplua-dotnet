# OpenAI preparation

Use O2 for the current portal sequence, O1 for package shape, O3 for policy and
annotations, O5 for OAuth, O6 for host testing, O7 for remote-app eligibility,
and O8 to interpret exact reported errors. Links are in [sources](sources.md).
Read live pages before relying on a release-sensitive rule.

## Package and listing

Use a portable root `plugin.json` and, if needed, `mcp.json`; keep skills under
`skills/`. Put OpenAI data under `extensions.com.openai`. Use an explicit
semantic version. Keep compatibility overlays synchronized; the OpenAI
extension takes precedence, so two manifests are not merged. If the extension
is absent, the Codex overlay supplies OpenAI settings; an empty inline object
does not fall back. Portable skills and `mcp.json` remain canonical regardless
of overlay component declarations. Codex compatibility packages instead declare
`mcpServers: "./.mcp.json"`; resolve it before deciding MCP review is inapplicable.

Provide `interface.category` from the current category list for the final public
listing. O2 marks it required; O8 describes an import default of Other when
omitted. The submission checker requires an explicit choice without claiming
that every import rejects omission. Private portable metadata can use defaults.

For final listing, check the display name and subtitle against 30 characters,
the long description against 4,000, and developer name against 80. Provide at
most three distinct single-line starter prompts of at most 128 characters.
Use actual square icons referenced inside the package. Check current image
rules in O8; avoid extrapolating screenshot rules to a plugin with no app UI.
Optional dark variants and colors should never block progress if declined.

A remote MCP submission needs four accessible HTTPS listing pages: website,
support, privacy policy, terms. Check their content and ownership, not just a
200 response. Skills-only metadata validation does not require all four.
Do not substitute a root homepage for a listing field. Drafting a policy is not
publishing it, and publisher decisions must come from the creator.

Author-supplied public uploads must exclude root `.app.json` and non-null
`apps` declarations, including hidden overlays. Preserve account-bound originals
and bindings generated by the portal in saved releases. Use actual endpoints,
not invented replacements. A public remote endpoint needs stable HTTPS; local
processes and test tunnels do not establish directory eligibility.

Lifecycle hooks are supported for manual/local use but packages with executable
lifecycle hooks are not eligible for the public directory (O2). Inspect the
effective hooks configuration, including the default `hooks/hooks.json` and
referenced hooks. A prose mention of hooks is not an executable declaration.
Keep a separate distribution if local hooks are needed.

## Review metadata and testing

For an initial remote MCP review, prepare exactly five positive and three
negative cases, a verified recording URL, release notes, and working reviewer
access when sign-in is needed. Skills-only plugins need no MCP cases or video.
O2 defines the current field mappings:

- One server: `extensions.com.openai.review.test_cases`, with `positive` and
  `negative`. Each case has `description` and `prompt`; positive cases also
  use string `tools_triggered` and `expected_behavior`.
- Multiple declared servers: cases belong to the exact server's OpenAI review
  extension using `testCases`/`negativeTestCases` and camelCase case fields.
  Do not combine these with plugin-level cases. Declaration of several servers
  does not mean the portal can connect all of them: it currently connects one.
- `review.demo_recording_url`, `review.commerce`, `review.commerce_description`.
- `publication.release_notes`, `publication.countries`, `publication.translations`.

Keep account credentials in secure portal fields, never metadata. Use a ready
test account with sample data; verify that sign-in requires no creator mailbox,
MFA approval, codes, magic link, or private network. Do not mark OpenAI functional verification complete until every submitted
review case has passed on each supported surface where the integration will
be available (O7). Record case × surface × source revision/package hash,
expected and observed outcomes, and execution evidence. Missing, failed, or
blocked cases remain visible. This is not a test of every historical or future
model. A local package pass cannot satisfy the gate.
Tool annotations require explicit boolean read-only, destructive, and open-world
hints. O3 says justifications are no longer required; older O7/O8 wording can
conflict. Verify current validation and report the conflict if it persists.

Use the [per-tool record](../templates/tool-review.md) for schemas, explicit
boolean `readOnlyHint`, `destructiveHint`, `openWorldHint`, permissions, side
effects and returned data. Presence of hints does not prove they are truthful.

## Portal and updates

After preparation, authorized upload creates a draft. Verify its identity,
imported metadata, skills scans, server/domain connection, authentication, and
review information. A verified publisher and eligible permissions are needed;
check the current project residency restriction in O7 if MCP review is involved.
Review submission and publication of an approved release are separate actions.

Use the existing plugin for updates. A complete replacement ZIP can change
skills/metadata; verify imported fields and preserved connection. An omitted
field may preserve saved state, while an empty value may clear it. Imported
cases can stay ZIP-owned. Read O2 before changing them. Do not overwrite an
active review or change its endpoint to bypass a limitation. Server tool updates
have their own scans and availability, separate from package publication.


## Desktop-only partner route

[Desktop-only submission](https://developers.openai.com/plugins/deploy/desktop-only)
permits local stdio MCP packages for approved, allowlisted partner organizations.
Select `--submission-route desktop-only` with `--desktop-allowlist <record.json>`.
Include runtime files and dependencies, and guide the creator through clean-install testing and portal
submission, checking the returned observations at each wizard step. The checker inspects a supplied confirmation record;
it cannot independently verify partner membership. A local-only package does
not inherit the remote endpoint's OAuth, five/three-case and video checks.

Portal upload, legal attestations, review submission and publication are external
human handoffs in this meta-tool. Current source-backed preflight findings and
review-material preparation are its deliverables.
